## What is Relationship, Strong vs Weak Relationship, Attribute Consistency Constraints, Type of Attributes, Degree of Relationship, Mapping cardinality?

Absolutely. These are the **next important ER Model concepts**. I'll connect them together using one running example: a **social-network database**.

---

# 1. Relationship

A **relationship** represents an association between two or more entities.

For example:

```text
USER ───── creates ───── POST
```

Here:

* `USER` → entity
* `POST` → entity
* `creates` → relationship

It tells us:

> A user creates a post.

Another example:

```text
STUDENT ───── enrolls in ───── COURSE
```

The relationship is `enrolls in`.

---

# 2. Relationship Type vs Relationship Instance

This distinction is similar to **Entity Type vs Entity Instance**.

### Relationship Type

The general definition:

```text
USER ───── creates ───── POST
```

This says users can create posts.

### Relationship Instance

A specific occurrence:

```text
Sailesh ───── creates ───── Post #101
```

So:

> **Relationship type = definition of the relationship**

> **Relationship instance = one specific occurrence of that relationship**

---

# 3. Strong vs Weak Relationship

This terminology can be confusing because it is closely related to **strong and weak entities**.

## Strong relationship / identifying relationship

A relationship is considered **identifying** when it is important for identifying a weak entity.

Example:

```text
EMPLOYEE ───── has ───── DEPENDENT
```

Suppose `DEPENDENT` is a weak entity.

```text
EMPLOYEE
employee_id PK
      |
      | identifies
      ↓
DEPENDENT
dependent_name
```

The dependent's identity depends on the employee.

Therefore, the relationship between them is an **identifying relationship**.

In traditional ER notation, this is represented using a **double diamond**.

```text
EMPLOYEE ═══ ◈ HAS ◈ ═══ DEPENDENT
```

### Important

Don't think:

> "Strong relationship = relationship that is more important."

Instead:

> **An identifying relationship connects a weak entity to its owner/strong entity and helps identify the weak entity.**

# 4. Attribute Consistency Constraints

This is essentially about:

> **What values are allowed for an attribute?**

For example:

```text
USER
----------------
user_id
name
age
email
```

We can impose constraints.

### Age

```text
age >= 0
```

A negative age shouldn't be allowed.

### Email

```text
email must be unique
```

### Name

```text
name cannot be NULL
```

These are **attribute-level constraints**.

In SQL, they can become:

```sql
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE,
    age INT CHECK (age >= 0)
);
```

So you can think:

```text
Attribute
    ↓
What values are allowed?
    ↓
Constraints
```

# 5. Types of Attributes

This is a very important ER topic.

There are several types.

## 5.1 Simple Attribute

Cannot be meaningfully divided further.

Example:

```text
age
salary
gender
```

```text
USER
 └── age
```

---

# 5.2 Composite Attribute

Can be divided into smaller attributes.

Example:

```text
name
 ├── first_name
 └── last_name
```

Or:

```text
address
 ├── street
 ├── city
 ├── state
 └── pincode
```

So:

```text
ADDRESS
   |
   ├── Street
   ├── City
   ├── State
   └── PIN
```

---

# 5.3 Single-Valued Attribute

Only one value for an entity.

Example:

```text
user_id
date_of_birth
```

A user has one date of birth.

---

# 5.4 Multivalued Attribute

Can have multiple values.

Example:

```text
USER
 └── phone_number
        ├── 9876543210
        └── 9123456780
```

One user can have multiple phone numbers.

Traditional ER notation represents a multivalued attribute using a **double oval**.

---

# 5.5 Stored Attribute

A value that is actually stored.

Example:

```text
date_of_birth
```

---

# 5.6 Derived Attribute

A value calculated from another attribute.

Example:

```text
date_of_birth
      ↓
     age
```

Age can be calculated from date of birth.

So:

```text
date_of_birth → stored
age           → derived
```

Traditional ER diagrams represent a derived attribute using a **dashed oval**.

---

# 5.7 Key Attribute

An attribute that uniquely identifies an entity.

Example:

```text
USER
----------------
user_id ← key
name
email
```

`user_id` uniquely identifies a user.

In ER diagrams, the key attribute is traditionally **underlined**.

---

# 6. Quick Attribute Summary

| Attribute type | Example               |
| -------------- | --------------------- |
| Simple         | Age                   |
| Composite      | Address → City, State |
| Single-valued  | Date of birth         |
| Multivalued    | Phone numbers         |
| Stored         | Date of birth         |
| Derived        | Age                   |
| Key            | User ID               |

One attribute can belong to multiple categories.

For example:

```text
user_id
```

is:

```text
Simple + Single-valued + Stored + Key
```

# 7. Degree of Relationship

**Degree tells us how many entity types participate in a relationship.**

There are three important ones:

```text
Unary
Binary
Ternary
```

---

# 8. Unary Relationship

**One entity type participates in the relationship.**

Example:

```text
EMPLOYEE ───── manages ───── EMPLOYEE
```

The same entity type participates twice.

One employee manages another employee.

```text
       manages
Employee ─────────→ Employee
```

This is a **unary relationship**.

Also called a **recursive relationship**.

Another example:

```text
USER ───── follows ───── USER
```

Same entity type on both sides.

Therefore:

> Degree = 1

---

# 9. Binary Relationship

Two entity types participate.

This is the most common.

Example:

```text
USER ───── creates ───── POST
```

Entity types:

```text
1. USER
2. POST
```

Therefore:

> Degree = 2

Another:

```text
STUDENT ───── enrolls ───── COURSE
```

Again:

> Binary relationship.

---

# 10. Ternary Relationship

Three entity types participate.

Example:

```text
SUPPLIER ── supplies ── PRODUCT ── to ── STORE
```

More formally:

```text
SUPPLIER
    \
     \
    SUPPLIES
     /    \
    /      \
PRODUCT   STORE
```

Three entity types participate:

```text
SUPPLIER
PRODUCT
STORE
```

Therefore:

> Degree = 3

This is a **ternary relationship**.

---

# 11. Degree Summary

| Degree  | Number of entity types | Example                            |
| ------- | ---------------------: | ---------------------------------- |
| Unary   |                      1 | Employee manages Employee          |
| Binary  |                      2 | User creates Post                  |
| Ternary |                      3 | Supplier supplies Product to Store |

### Easy trick

> **Degree = How many entity types are participating?**

Not how many entities exist.

---

# 12. Mapping Cardinality

Now we reach one of the **most important ER concepts**.

Mapping cardinality tells us:

> **How many entities of one entity type can be associated with entities of another entity type?**

The common types are:

```text
1 : 1
1 : N
N : 1
M : N
```

---

# 13. One-to-One (1:1)

Example:

```text
USER ───── has ───── PROFILE
```

One user has one profile.

One profile belongs to one user.

```text
USER 1 ───────── 1 PROFILE
```

Examples:

```text
Person ─── Passport
Employee ─── Locker
User ─── Profile
```

---

# 14. One-to-Many (1:N)

Example:

```text
USER ───── creates ───── POST
```

One user can create many posts.

But each post belongs to one user.

```text
USER 1 ───────── N POST
```

For example:

```text
                 ┌── Post 1
Sailesh ─────────┼── Post 2
                 └── Post 3
```

This is **1:N**.

---

# 15. Many-to-One (N:1)

This is simply the reverse perspective.

Same relationship:

```text
USER 1 ───── creates ───── N POST
```

If you're looking from the **POST side**:

```text
POST N ───── created by ───── 1 USER
```

Therefore:

```text
1:N
```

and

```text
N:1
```

can describe the **same relationship from opposite directions**.

---

# 16. Many-to-Many (M:N)

Example:

```text
USER ───── follows ───── USER
```

One user can follow many users.

One user can also be followed by many users.

```text
USER M ───────── N USER
```

Another classic example:

```text
STUDENT ───── enrolls ───── COURSE
```

A student can enroll in many courses.

A course can have many students.

```text
STUDENT M ───── N COURSE
```

---

# 17. Mapping Cardinality vs Degree

These two are **very commonly confused**.

### Degree

Asks:

> **How many entity types participate?**

Example:

```text
USER ─── creates ─── POST
```

Two entity types:

```text
USER
POST
```

Therefore:

```text
Degree = 2
```

Binary relationship.

---

### Cardinality

Asks:

> **How many instances can participate?**

```text
USER 1 ─── creates ─── N POST
```

Therefore:

```text
Cardinality = 1:N
```

---

# 18. Don't Mix These Up

Consider:

```text
USER ───── follows ───── USER
```

What is the degree?

There is only **one entity type**:

```text
USER
```

Even though USER appears twice.

Therefore:

```text
Degree = 1
```

It's a **unary relationship**.

But the cardinality is:

```text
M:N
```

because one user can follow many users and one user can be followed by many users.

So:

```text
Degree     = 1
Cardinality = M:N
```

This is a great exam/interview question.

---

# 19. Putting Everything Together

Consider:

```text
EMPLOYEE ───── manages ───── EMPLOYEE
```

### Relationship

`manages`

### Degree

One entity type:

```text
EMPLOYEE
```

Therefore:

```text
Unary
```

### Cardinality

One manager can manage many employees:

```text
1:N
```

So:

```text
EMPLOYEE 1 ───── manages ───── N EMPLOYEE
```

---

Another:

```text
USER ───── creates ───── POST
```

### Relationship

`creates`

### Degree

Two entity types:

```text
USER
POST
```

Therefore:

```text
Binary
```

### Cardinality

One user → many posts:

```text
1:N
```

# 20. Final Cheat Sheet

```text
RELATIONSHIP
    ↓
Association between entities
    │
    ├── Degree
    │      ↓
    │   How many entity TYPES participate?
    │
    │   Unary   → 1
    │   Binary  → 2
    │   Ternary → 3
    │
    └── Cardinality
           ↓
       How many entity INSTANCES can participate?

       1:1
       1:N
       N:1
       M:N
```

And:

```text
ATTRIBUTE
   │
   ├── Simple
   ├── Composite
   ├── Single-valued
   ├── Multivalued
   ├── Stored
   ├── Derived
   └── Key
```

And the relationship with weak entities:

```text
Strong Entity
      │
      │ identifying relationship
      ↓
Weak Entity
```

### The 3 questions to ask whenever you see an ER diagram

**1. What are the entities?**
→ Things/objects being represented.

**2. How are they related?**
→ Relationship.

**3. What are the numbers?**
→ Degree tells you **how many entity types**; cardinality tells you **how many instances can be associated**.

That last distinction — **degree vs cardinality** — is especially worth memorizing.
