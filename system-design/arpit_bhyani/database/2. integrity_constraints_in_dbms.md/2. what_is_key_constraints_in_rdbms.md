## Key Constraint in DBMS

A **Key Constraint** is a rule that ensures that **certain attribute(s) can uniquely identify an entity/record** in a relation.

In simple terms:

> **A key constraint prevents two rows from having the same key value.**

### Example

Consider a `Student` table:

| Student_ID | Name  | Email                                     |
| ---------: | ----- | ----------------------------------------- |
|        101 | Alice | [alice@gmail.com](mailto:alice@gmail.com) |
|        102 | Bob   | [bob@gmail.com](mailto:bob@gmail.com)     |
|        103 | John  | [john@gmail.com](mailto:john@gmail.com)   |

Here, `Student_ID` can uniquely identify every student.

```text
Student_ID
   ↓
101 → Alice
102 → Bob
103 → John
```

So `Student_ID` is a **key**.

This would violate the key constraint:

| Student_ID | Name  |
| ---------: | ----- |
|        101 | Alice |
|        101 | Bob ❌ |

because `101` identifies two different students.

## Key Constraint in the ER Model

This is slightly different from SQL's `PRIMARY KEY` terminology.

Suppose we have:

```text
STUDENT
---------
Student_ID
Name
Email
Phone
```

If `Student_ID` uniquely identifies a student:

```text
Student_ID → uniquely identifies STUDENT
```

then `Student_ID` satisfies the **key constraint**.

In an ER diagram, a key attribute is typically **underlined**:

```text
        STUDENT
       /       \
  Student_ID   Name
     _____
```

## Key Constraint vs Other Constraints

| Constraint                 | Main purpose                                                 |
| -------------------------- | ------------------------------------------------------------ |
| **Key Constraint**         | Ensures uniqueness/identification                            |
| **Entity Integrity**       | Primary key cannot be NULL                                   |
| **Referential Integrity**  | Foreign key must reference a valid row                       |
| **Domain Constraint**      | Values must belong to a valid domain                         |
| **Cardinality Constraint** | Controls how many entities can participate in a relationship |

### One important distinction

**Key constraint ≠ Primary Key**

A **key** is a concept used to uniquely identify records.

A **primary key** is the particular key chosen as the main identifier for a table.

For example:

```text
Student_ID → Candidate Key
Email      → Candidate Key
```

If we choose `Student_ID` as the main identifier:

```text
Student_ID → Primary Key
Email      → Alternate Candidate Key
```

So, in short:

> **Key Constraint = uniqueness requirement that allows an entity/tuple to be uniquely identified.**
