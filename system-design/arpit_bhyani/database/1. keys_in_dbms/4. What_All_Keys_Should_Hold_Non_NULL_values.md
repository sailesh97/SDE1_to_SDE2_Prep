If you're asking **which keys must be NOT NULL**, the easiest way is to separate **"must be non-null"** from **"can be non-null."**

### 🔑 NULL rules for different keys

| Key               | Must be NOT NULL? | Why?                                                       |
| ----------------- | ----------------- | ---------------------------------------------------------- |
| **Primary Key**   | ✅ **Yes**         | A row must always have an identity                         |
| **Candidate Key** | ✅ **Yes**         | Must uniquely identify every row                           |
| **Alternate Key** | ✅ **Yes***        | As a candidate key, it must identify rows                  |
| **Super Key**     | ❌ Not necessarily | Depends on the DBMS/definition and participating columns   |
| **Foreign Key**   | ❌ Not necessarily | Relationship can be optional                               |
| **Unique Key**    | ❌ Not necessarily | NULL handling is DBMS-specific                             |
| **Composite Key** | Depends           | Depends on whether it is a PK/candidate key and DBMS rules |
| **Natural Key**   | Depends           | Depends on whether it is defined as a candidate/unique key |
| **Surrogate Key** | Depends           | Usually NOT NULL when used as a PK                         |

### The most important one

**Primary Key:**

```sql
student_id INT PRIMARY KEY
```

This automatically means:

```text
UNIQUE + NOT NULL
```

You cannot have:

```text
student_id
-----------
101
102
NULL   ❌
```

---

## Foreign Key is different

Consider:

```text
STUDENT
---------------------------
student_id | department_id
101        | 10
102        | 20
103        | NULL
```

`department_id` can be `NULL` if the relationship is optional.

For example:

> Student 103 hasn't been assigned to a department yet.

So a Foreign Key **can be NULL**.

```sql
department_id INT,
FOREIGN KEY (department_id)
    REFERENCES department(department_id)
```

If you want to prevent that:

```sql
department_id INT NOT NULL,
```

---

## Unique Key is a common confusion

Consider:

```sql
email VARCHAR(100) UNIQUE
```

Whether `NULL` is allowed and how many NULLs are allowed is **DBMS-dependent**.

For example, in MySQL, a normal `UNIQUE` constraint permits multiple `NULL` values because `NULL` is not considered equal to another `NULL`.

If you want:

> **Unique + definitely present**

use:

```sql
email VARCHAR(100) NOT NULL UNIQUE
```

# 🧠 Best way to remember

### **Primary Key → Unique + NOT NULL**

```text
          Primary Key
          /         \
      UNIQUE       NOT NULL
```

### **Foreign Key → Can be NULL**

```text
Foreign Key
     ↓
Can be NULL
     ↓
unless explicitly declared NOT NULL
```

### **Unique Key → NULL depends on DBMS**

```text
Unique
  ↓
UNIQUE values
  +
NULL behavior → DBMS-specific
```

### One important correction to keep in mind

A **Candidate Key**, by definition, is a minimal set of attributes that uniquely identifies tuples. In practical SQL schema design, if you declare something as a candidate key, you normally enforce it as **UNIQUE + NOT NULL**. Otherwise, SQL's special treatment of `NULL` means the constraint may not behave as a true candidate-key constraint.

So for exams, remember:

> **Primary Key → definitely NOT NULL**
> **Candidate Key → conceptually NOT NULL**
> **Foreign Key → can be NULL**
> **Unique Key → may allow NULL depending on DBMS**

# Why Candidate Keys are conceptually Non_NULL?

Yes. The key word is **“conceptually.”**

A **Candidate Key** is defined as:

> **A minimal set of attributes that can uniquely identify every row in a relation.**

The phrase **“every row”** is why a candidate key is conceptually **NOT NULL**.

### Let's use an example

Suppose we have:

| student_id | email                                     | name  |
| ---------: | ----------------------------------------- | ----- |
|        101 | [rahul@gmail.com](mailto:rahul@gmail.com) | Rahul |
|        102 | [priya@gmail.com](mailto:priya@gmail.com) | Priya |
|        103 | [amit@gmail.com](mailto:amit@gmail.com)   | Amit  |

Suppose `email` is a Candidate Key.

Why?

```text
email
 ↓
uniquely identifies each student
```

So:

```text
rahul@gmail.com → Rahul
priya@gmail.com → Priya
amit@gmail.com  → Amit
```

Now imagine:

| student_id | email                                     | name  |
| ---------: | ----------------------------------------- | ----- |
|        101 | [rahul@gmail.com](mailto:rahul@gmail.com) | Rahul |
|        102 | **NULL**                                  | Priya |
|        103 | [amit@gmail.com](mailto:amit@gmail.com)   | Amit  |

Can `email` now identify **every student**?

**No.**

For student 102, we don't have an email value with which to identify them.

That's why, conceptually:

```text
Candidate Key
     ↓
Must identify every row
     ↓
Therefore
     ↓
Cannot be NULL
```

---

## But why do we say "conceptually"?

Because **SQL and relational theory are slightly different here.**

In pure relational theory, a candidate key cannot contain `NULL`.

But SQL has a special concept of `NULL` meaning:

> "Unknown / missing value"

And SQL's `UNIQUE` constraint can behave differently with `NULL`.

For example, in MySQL:

```sql
CREATE TABLE student (
    student_id INT PRIMARY KEY,
    email VARCHAR(100) UNIQUE
);
```

MySQL can allow:

| student_id | email                             |
| ---------: | --------------------------------- |
|        101 | [a@gmail.com](mailto:a@gmail.com) |
|        102 | NULL                              |
|        103 | NULL                              |

The `UNIQUE` constraint doesn't necessarily make `email` a true candidate key because `NULL` isn't treated like an ordinary value.

So:

```text
UNIQUE constraint ≠ automatically Candidate Key
```

---

# Candidate Key vs UNIQUE constraint

This is the important distinction:

### Candidate Key — theoretical concept

```text
Must:
✓ Uniquely identify every tuple
✓ Be minimal
✓ Not contain NULL
```

### UNIQUE constraint — SQL implementation

```text
Ensures:
✓ Non-NULL values don't violate uniqueness

NULL:
⚠ Behavior depends on DBMS
```

Therefore, if you want `email` to actually behave as a candidate key in MySQL, you'd typically write:

```sql
email VARCHAR(100) NOT NULL UNIQUE
```

Now you have:

```text
email
 ↓
NOT NULL
 +
UNIQUE
 ↓
Can uniquely identify every student
 ↓
Candidate Key
```

### 🔥 Remember this

> **Candidate Key is a theoretical concept. UNIQUE is a SQL constraint.**

That's why saying **"Candidate Key → conceptually NOT NULL"** is more precise than simply saying **"Candidate Key → NOT NULL"**.
