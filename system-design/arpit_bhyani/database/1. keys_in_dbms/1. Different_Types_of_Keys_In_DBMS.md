In **RDBMS (Relational Database Management System)**, keys are attributes (or combinations of attributes) used to **uniquely identify rows** and establish relationships between tables.

Let's use this simple example throughout:

### `STUDENT`

| student_id | email                             | name  | phone | department_id |
| ---------: | --------------------------------- | ----- | ----- | ------------: |
|        101 | [a@gmail.com](mailto:a@gmail.com) | Rahul | 98765 |            10 |
|        102 | [b@gmail.com](mailto:b@gmail.com) | Priya | 98766 |            20 |
|        103 | [c@gmail.com](mailto:c@gmail.com) | Amit  | 98767 |            10 |

### Main types of keys

| Key               | Meaning                                           | Example                                                     |
| ----------------- | ------------------------------------------------- | ----------------------------------------------------------- |
| **Super Key**     | Any attribute(s) that can uniquely identify a row | `{student_id}`, `{student_id, name}`, `{student_id, email}` |
| **Candidate Key** | Minimal Super Key                                 | `{student_id}`, `{email}`                                   |
| **Primary Key**   | Candidate Key chosen to uniquely identify rows    | `student_id`                                                |
| **Alternate Key** | Candidate Key not selected as Primary Key         | `email`                                                     |
| **Foreign Key**   | Attribute that references a key in another table  | `department_id`                                             |
| **Composite Key** | Key made up of 2+ attributes                      | `{student_id, course_id}`                                   |
| **Unique Key**    | Constraint ensuring values are unique             | `email`                                                     |
| **Natural Key**   | Real-world meaningful attribute used as a key     | `email`                                                     |
| **Surrogate Key** | Artificial/system-generated key                   | `student_id`                                                |

---

## 1. Super Key

A **Super Key** is any combination of attributes that can **uniquely identify a row**.

For our `STUDENT` table:

```text
{student_id}
{student_id, name}
{student_id, email}
{student_id, phone}
{email}
{email, name}
```

All of these can uniquely identify a student.

So they are **Super Keys**.

### Important

A Super Key may contain **unnecessary attributes**.

For example:

```text
{student_id, name}
```

`student_id` alone is already unique, so `name` is unnecessary.

---

## 2. Candidate Key

A **Candidate Key** is a **minimal Super Key**.

"Minimal" means:

> You cannot remove any attribute from it and still uniquely identify the row.

For example:

```text
student_id
email
```

Both uniquely identify students.

Therefore:

```text
Candidate Keys = {student_id}, {email}
```

Notice:

```text
{student_id, name}
```

is **not** a Candidate Key because `name` is unnecessary.

### Relationship

```text
Super Key
    ↓
Remove unnecessary attributes
    ↓
Candidate Key
```

---

## 3. Primary Key

The **Primary Key** is the Candidate Key that we choose as the **main identifier** for the table.

Suppose we have:

```text
Candidate Keys:
    student_id
    email
```

We choose:

```text
student_id
```

as the Primary Key.

```sql
CREATE TABLE student (
    student_id INT PRIMARY KEY,
    email VARCHAR(100),
    name VARCHAR(100)
);
```

A Primary Key must be:

* **Unique**
* **NOT NULL**

A table can have **only one Primary Key**, although that Primary Key can consist of multiple columns.

---

## 4. Alternate Key

A Candidate Key that **wasn't chosen as the Primary Key** is called an **Alternate Key**.

Suppose:

```text
Candidate Keys:
    student_id
    email
```

We select:

```text
student_id → Primary Key
```

Then:

```text
email → Alternate Key
```

So:

```text
Candidate Keys
       ↓
 ┌─────┴─────┐
 ↓           ↓
Primary    Alternate
 Key         Key
```

---

## 5. Foreign Key

A **Foreign Key** is used to create a **relationship between two tables**.

Suppose we have:

### `DEPARTMENT`

| department_id | department_name  |
| ------------: | ---------------- |
|            10 | Computer Science |
|            20 | Electronics      |

And:

### `STUDENT`

| student_id | name  | department_id |
| ---------: | ----- | ------------: |
|        101 | Rahul |            10 |
|        102 | Priya |            20 |
|        103 | Amit  |            10 |

Here:

```text
DEPARTMENT
department_id ← Primary Key
       ↑
       │
       │ Foreign Key
       │
STUDENT
department_id
```

`STUDENT.department_id` is a **Foreign Key** referencing `DEPARTMENT.department_id`.

```sql
CREATE TABLE student (
    student_id INT PRIMARY KEY,
    name VARCHAR(100),
    department_id INT,
    FOREIGN KEY (department_id)
        REFERENCES department(department_id)
);
```

### Purpose

Foreign Keys maintain **referential integrity**.

For example, you shouldn't normally be able to insert:

```text
student_id = 104
department_id = 999
```

if department `999` doesn't exist.

---

## 6. Composite Key

A **Composite Key** consists of **two or more columns**.

Consider a student enrolling in courses.

### `ENROLLMENT`

| student_id | course_id | enrollment_date |
| ---------: | --------: | --------------- |
|        101 |       501 | 2026-08-01      |
|        101 |       502 | 2026-08-02      |
|        102 |       501 | 2026-08-03      |

Here:

```text
student_id alone ❌
course_id alone  ❌

student_id + course_id ✅
```

Therefore:

```text
(student_id, course_id)
```

can be the Composite Primary Key.

```sql
PRIMARY KEY (student_id, course_id)
```

This is very common in **many-to-many relationships**.

---

## 7. Unique Key

A **Unique Key** is a database constraint that prevents duplicate values.

For example:

```sql
CREATE TABLE student (
    student_id INT PRIMARY KEY,
    email VARCHAR(100) UNIQUE,
    name VARCHAR(100)
);
```

This prevents:

```text
student 101 → a@gmail.com
student 102 → a@gmail.com ❌
```

### Primary Key vs Unique Key

| Primary Key        | Unique Key                       |
| ------------------ | -------------------------------- |
| Identifies the row | Ensures uniqueness               |
| Only one per table | Multiple possible                |
| Cannot be NULL     | NULL handling depends on DBMS    |
| Main identifier    | Additional uniqueness constraint |

---

## 8. Natural Key

A **Natural Key** is a key that has **real-world meaning**.

Examples:

```text
email
PAN number
ISBN
passport number
employee number
```

For example:

```text
email = "rahul@gmail.com"
```

The value already exists for a real-world reason.

---

## 9. Surrogate Key

A **Surrogate Key** is an **artificial/system-generated identifier** with no business meaning.

For example:

```text
student_id
101
102
103
```

The number `101` doesn't inherently describe the student.

It is simply an identifier generated by the system.

Example:

```sql
student_id INT AUTO_INCREMENT PRIMARY KEY
```

### Natural vs Surrogate

| Natural Key                | Surrogate Key       |
| -------------------------- | ------------------- |
| Has business meaning       | No business meaning |
| Comes from real-world data | Generated by system |
| Example: email             | Example: student_id |
| Can potentially change     | Usually stable      |

---

# The most important relationship to remember

This is probably the **most important part for DBMS exams/interviews**:

```text
                    SUPER KEY
                       │
             Remove unnecessary
                attributes
                       ↓
                 CANDIDATE KEY
                  /          \
                 /            \
                ↓              ↓
        PRIMARY KEY      ALTERNATE KEY
```

And separately:

```text
PRIMARY KEY
     │
     │ referenced by
     ↓
FOREIGN KEY
     │
     ↓
Creates relationship between tables
```

And:

```text
COMPOSITE KEY
     =
Multiple attributes together
     ↓
(student_id, course_id)
```

### Quick hierarchy

| Concept           | Think of it as                    |
| ----------------- | --------------------------------- |
| **Super Key**     | Anything that uniquely identifies |
| **Candidate Key** | Minimal Super Key                 |
| **Primary Key**   | Candidate Key we choose           |
| **Alternate Key** | Candidate Key we don't choose     |
| **Foreign Key**   | Link to another table's key       |
| **Composite Key** | Key made of multiple columns      |
| **Unique Key**    | Enforces uniqueness               |
| **Natural Key**   | Real-world identifier             |
| **Surrogate Key** | Artificial identifier             |

**One subtle point:** Composite key is not really a completely separate "level" like Super/Candidate/Primary. A **composite key can itself be a candidate key, primary key, or foreign key**, depending on how it is used.
