If by **"unique"** you mean **"can uniquely identify a row in an RDBMS"**, then the answer is:

### Keys that can uniquely identify a row

| Key               | Can uniquely identify a row? | Why?                                          |
| ----------------- | ---------------------------- | --------------------------------------------- |
| **Super Key**     | ✅ Yes                        | By definition, it uniquely identifies a row   |
| **Candidate Key** | ✅ Yes                        | It is a minimal Super Key                     |
| **Primary Key**   | ✅ Yes                        | It is the chosen Candidate Key                |
| **Alternate Key** | ✅ Yes                        | It is an unselected Candidate Key             |
| **Unique Key**    | ✅ Yes*                       | Enforces uniqueness on its column(s)          |
| **Composite Key** | ✅ Yes                        | If the combination is unique                  |
| **Natural Key**   | ✅ Yes*                       | If the natural attribute is guaranteed unique |
| **Surrogate Key** | ✅ Yes                        | Designed to uniquely identify rows            |
| **Foreign Key**   | ❌ Not necessarily            | Multiple rows can reference the same value    |

### The easiest way to understand it

Consider:

```text
STUDENT
------------------------------
student_id | email | dept_id
101        | a@x.com | 10
102        | b@x.com | 10
103        | c@x.com | 20
```

#### `student_id`

```text
101
102
103
```

Unique → **Yes**

Could be:

> Super Key + Candidate Key + Primary Key + Surrogate Key

#### `email`

```text
a@x.com
b@x.com
c@x.com
```

Unique → **Yes**

Could be:

> Super Key + Candidate Key + Alternate Key + Natural Key

#### `dept_id`

```text
10
10
20
```

Not unique → **No**

It's a **Foreign Key**, because multiple students can belong to the same department.

---

### 🔥 The important distinction

Don't think:

> "Foreign Key = unique"

A Foreign Key's purpose is **relationship**, not uniqueness.

For example:

```text
Department
10 → CSE
20 → ECE

Student
101 → 10
102 → 10
103 → 10
104 → 20
```

`department_id = 10` appears three times.

That's perfectly valid.

So:

```text
Primary Key    → MUST be unique
Candidate Key  → MUST be unique
Alternate Key  → MUST be unique
Super Key      → MUST be unique
Foreign Key    → DOES NOT have to be unique
```

### One very useful rule

> **Every Candidate Key is a Super Key, but every Super Key is NOT a Candidate Key.**

And:

> **A Primary Key is always unique, but a Foreign Key does not have to be unique.**

* For **Unique Key, Natural Key, and Surrogate Key**, uniqueness depends on how the database schema defines/uses them.
